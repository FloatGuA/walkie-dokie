## 成熟度分三档，别混着处理

### 已经可以直接执行（有完整设计，走 TDD 就行）

**debounce+graph 并发场景补测试**——设计已在对话里过完、用户已确认，完整 bite-sized 实现计划见 [docs/superpowers/plans/2026-08-20-debounce-graph-concurrency-tests.md](superpowers/plans/2026-08-20-debounce-graph-concurrency-tests.md)。里面已经用 spike 脚本验证过现有 `UserLocks` 机制在两个并发场景下都是正确的，任务是"补真并发回归测试"而不是"修 bug"，plan 里写清楚了。直接用 `superpowers:subagent-driven-development` 或 `superpowers:executing-plans` 按 plan 执行即可，不需要再брейнsторм。

### 有高层设计，但细节不够写 plan（先补设计，再写 plan）

**记忆压缩（compaction）**——`DECISION.md` 2026-08-17 那条"短期历史压缩（compaction）设计稿：带证据、增量合并、独立轻量模型"已经拍板了架构方向（evidence-based、增量合并、独立轻量模型、否掉了哪些方案），但**没有**：
- `SummaryValidator` 的具体校验规则（复用 `MemoryRepository.validate()`的"校验哲学"，但没写字段级规则）
- 触发阈值（现在硬截断是 12 条/单条 2,000 字/总计 12,000 字符；新设计什么时候触发"对新被截断的一批生成摘要"、二级压缩什么时候触发，都没定数字）
- `conversation_summary` channel 的具体数据结构（字段、类型）
- "独立轻量模型 client"具体是谁（DeepSeek 更小的模型？换供应商？）

这些是会影响接口设计和测试用例的真实决策点，不是实现细节可以自己顺手补的。**下一步是走一轮 `superpowers:brainstorming`（架构路径，因为要新建 `conversation_summary` channel 这个新接口），把上面几条问清楚、写成 spec，再用 `superpowers:writing-plans` 转成 plan。** 不要跳过这一步直接写代码——这正是本项目 CLAUDE.md 里"对齐优先，绝不臆测"那条规则要防的情况。

### 完全没有设计（先弄清楚要不要做、怎么做）

以下三项目前只是 `docs/agent-system-self-check.md` 里的问题陈述，没有任何设计决策，需要从头 `superpowers:brainstorming`：

- **Guardrails（输入侧）**——用户原文喂进 `main_agent` 决策前没有 prompt-injection 检测（输出侧已经有 Office 主动内容校验 + 执行 agent 最小权限沙箱，方向已验证有效，可以参考）。开放性问题：要不要引入检测？规则式还是模型判断？如果模型判断，是否违反"Models judge, code decides"里"分类可以用模型"这条（CLAUDE.md 第 9 条），还是应该走确定性规则？
- **成本与延迟预算**——DeepSeek/Claude/Codex 都是按量计费，目前没有 token 用量/单用户成本埋点。开放性问题：埋点粒度（每轮？每用户每天？）、超限后的行为（拒绝执行？告警？限速？）、谁来看这些数据（暂时只有开发者本人，要不要现在就做 UI）。
- **人工兜底路径**——`ask_confirm` 循环里如果用户连续说不清楚/连续失败，目前没有"转人工"或"明确说做不到"的出口。PROGRESS.md P2 提到"针对中老年用户重新设计确认、纠错、失败恢复"，但没有具体方案。这个可能需要先跟用户对齐目标用户画像（P2 里提到的"中老年用户"）再设计交互，不是纯技术决策。

另外 **Evaluation harness（golden set 回归）** 严格说界于第二档和第三档之间：`DECISION.md` 里有一条"Golden Evaluation 遇到单个样本执行异常时保持 fail-fast"的执行策略决策，但"golden set 里具体放哪些样本、怎么组织、CI 里怎么跑"完全没设计过，实际上也需要走一轮 brainstorming。

## 建议顺序

1. 先把已经批准的 debounce+graph 并发测试 plan 执行掉（15-30 分钟量级，纯收尾）。
2. 剩下四项（compaction、guardrails、成本预算、人工兜底、eval harness）都需要先跟用户 brainstorming。**不要因为要交给"更强的模型"就跳过跟用户对齐这一步**——这些都是需要用户拍板的产品/架构决策，模型能力强弱不改变这一点。建议先问用户想先做哪个，而不是自己排优先级替用户决定（虽然 `docs/agent-system-self-check.md` 里我标了 eval harness 和 compaction 优先级"高"，那只是建议，不是拍板）。
